# Kairos repository audit — 2026-11-10

Static audit of the desktop (Python) and iOS (Swift) code, plus a handful of measurements and
reproductions. **No source file was changed.** Baseline before the audit: 95 passed in
`test_ios_import / test_ios_sync / test_ios_pairing / test_ios_parity / test_gate0`.

## 0. What this audit did and did not cover (read this first)

The repo is 52.7k lines of Python and 10.7k of Swift (plus a 5.9k-line `map_vault.html`). It was not
possible to read every line in one session, so coverage is uneven. Do not read "no finding" as
"verified clean" for anything in the third list.

**Read in full, line by line:** `database.py`, `sync_server.py`, `scanner.py`, `config.py`,
`crash_guard.py`, `fs_atomic.py`, `cloud_files.py` (head), `siglip_engine.py` (download),
`locked_folder.py` (lines 1-420), `data_migration.py` (120-297); iOS `SyncEngine`, `ImportQueue`,
`PhoneBackup`, `AppModel`, `SQLiteDatabase`, `LibraryStore`, `SyncClient`, `FetchQueue`,
`LibraryGridView`, `RootTabView`, `PairingView`.

**Scanned with targeted greps / AST across the whole tree:** subprocess calls without timeout,
swallowed exceptions, `processEvents`, raw `sqlite3.connect`, hidden-folder filtering per data module,
outbound network use, `logging` use, `main.py` class/method sizes, iOS discovery / a11y / i18n /
background-session / backup-exclusion APIs; `main.py` read only around lines 286-312, 3125-3160,
4410-4430, 5060-5130, 5270-5365, 7640-7790.

**Not read (no opinion):** most of `main.py` (~7,600 lines), `viewer*.py`, `ui_*.py`,
`settings_dialog.py` (apart from two calls), `face_engine.py`, `face_cluster.py`, `map_host.py`,
`tile_store.py`, `map_precache.py`, `privacy_export.py` (apart from its exiftool call), `events_view`,
`albums_view`, `echoes_view`, `reels_view`, `quick_edit`, `imaging`, `color_manage`, every JS/HTML
file, ~35 iOS UI files (Viewer, Map, Edit, Events, People, Search, Hidden, PhotoPicker, ImageLoader
body), and all tests except as a baseline run.

**Not done:** no runtime/visual inspection of either UI (no Xcode here; screen capture is off-limits
on this machine), no frame-rate or memory profiling, no iOS compilation. UX findings are therefore
from code, not from looking at pixels.

**Measured / reproduced in this session** (scripts in the job tmp dir, not in the repo):
Live-Photo pairing query, R*Tree float32 drift, exiftool with non-ASCII names, WCAG contrast of the
palette, HTTP keep-alive desync and duplicate-upload race against a real in-process `SyncServer`.

Status of the working tree at audit time: `sync_server.py` and `test_ios_import.py` have uncommitted
edits (server half of the 507 / free-space contract). Finding H1 depends on that.

## 1. [CRITICAL / HIGH]

### H1. iOS backup state machine reports "sent" for things that were dropped — FIXED in Fix Block A (see `test_block_a_integrity.py`, `BackupIntegrityTests.swift`; Swift not compiled here)
- **Location:** `ios/.../Sync/ImportQueue.swift` `drain` (l.113-132), `finish` (146-152), `retryLater` (155-164);
  `ios/.../Phone/PhoneBackup.swift` `run` step 4 (l.110-117).
- **Issue:** An asset is marked `sent` when its hash "left the outbox", not when the desktop acknowledged it.
  `finish(sent:false)` (400/411/413/415), five 5xx answers, and `retryLater` all remove the item from the
  outbox, so step 4 then flags the asset `sent`. 507 and 503 are counted as failures too, although the
  server comment in `sync_server._import` says the phone treats them as "pause and keep the file".
  After five passes against a full desktop disk the photos are dropped and shown as backed up. `BackupState.failed`
  is never set. For Live Photos only the still's hash is stored, so the asset turns `sent` while the motion
  half may still be queued.
- **Fix:** Return an explicit per-item result from `drain` (`acked`, `rejected(reason)`, `deferred`). Only `acked`
  (200 `imported`/`duplicate`, or `present`) may set `sent`. Rejected -> `failed` with the reason, shown in the UI.
  507/503/5xx/timeouts never increment `failures`; they park the item with `retryAfter`. Track one row per file
  (still + motion) and mark the asset `sent` only when all of its files are acked.

### H2. Re-pairing leaves the old SyncEngine running and fighting the new one
- **Location:** `ios/.../Root/AppModel.swift` `connect` (l.89-121) and `pair` (124-135).
- **Issue:** `connect` overwrites `engine`/`client` without stopping the previous engine, and the previous engine's
  `observe(status:)` closure still writes `self.status`. After re-scanning a QR (the only recovery from an IP change,
  see H7) the old loop keeps reconnecting to the old endpoint and flips the badge to Offline/needsPairing while the new
  one is Live. Two engines also apply pages to the same store.
- **Fix:** `await engine?.stop()` and clear its callbacks before replacing; give each engine a generation id and drop
  callbacks from stale generations.

### H3. A favourite toggled offline is lost (and silently reverted)
- **Location:** `SyncEngine.setFavorite` (l.110-113), `AppModel.toggleFavorite` (296-300), `LibraryStore.setFavoriteLocally` (525-530).
- **Issue:** The local row is written, then the PUT throws offline and the error is swallowed with `try?`. Nothing is queued.
  The next journal upsert for that item overwrites the local flag with the desktop's value. Edits have a `dirty` queue; favourites do not.
- **Fix:** Add `fav_dirty` to `media_items` (or a small `pending_ops` table), push it in the same loop as `pushEdits`,
  and make `upsert` keep the local value while the flag is dirty.

### H4. Unpair is one tap, has no confirmation, wipes unsent work, and leaves false "backed up" states
- **Location:** `LibraryGridView.swift` menu (l.58-62); `AppModel.unpair` (137-158); `LibraryStore.reset` (125-134).
- **Issue:** `reset()` drops dirty edits and clears the replica, but `phone_assets.backup` stays `queued`/`sent`.
  Paired later with another desktop, those assets are considered backed up and never uploaded.
- **Fix:** Confirmation dialog stating what is lost (N unsent edits, N queued uploads). In `reset()` set
  `backup = 'none'` (keep `approved` if the user approved), clear `sha256` matches, and warn before discarding dirty edits.

### H5. UI stalls during sync: one locked connection, global `revision`, timeline rebuilt on the main actor
- **Location:** `SQLiteDatabase.swift` (single handle + `NSRecursiveLock`); `LibraryStore.apply` (l.147-173);
  `AppModel.connect` change callback (l.111-118); `LibraryGridView` `.task(id: TaskKey)` (l.80-83).
- **Issue:** A 2,000-row page runs inside one transaction holding the lock; the main actor's `timeline()`/`media()` reads
  wait on the same lock. Every page, and every 300-asset camera-roll index batch, also bumps `revision`, which re-queries
  the whole timeline (20k+ rows), regroups and re-matches. `media(id)` decodes the full JSON payload per cell.
- **Fix:** Open a second read-only WAL connection for the UI and keep the writer separate. Replace the single `revision`
  with per-domain counters (`mediaRevision`, `eventsRevision`, `editsRevision`) and diff the timeline in a detached task.
  Promote the few fields the grid needs (`thumbKey`, `has_thumb`, `fingerprint`) to real columns.

### H6. Scroll position `@State` in the grid parent re-runs the whole grid body every frame
- **Location:** `LibraryGridView.swift` `scrollFraction` (l.21, 191-196).
- **Issue:** `scrollFraction` is read only by the scrubber overlay but lives on the parent, so each scroll tick re-evaluates
  the body and re-diffs `ForEach(sections)` over every entry.
- **Fix:** Move it into the scrubber (own `@State`/small `@Observable`), or update only while `scrolling` and throttle to ~20 Hz.

### H7. No discovery and no IP re-discovery: sync dies silently after the router hands out a new address
- **Location:** `SyncClient.request` (l.73-91, fixed `endpoint.host`); `sync_server.lan_address` (l.556-565);
  no `NWBrowser`/`NWPathMonitor`/Bonjour anywhere in `ios/` (grep); no mDNS advertisement on the desktop.
- **Issue:** The IP from the QR is permanent. A DHCP renewal, a router reboot, or a different Wi-Fi leaves the phone "Offline"
  forever; the only fix is re-pairing (and see H2). `lan_address()` picks the interface routed to 10.255.255.255, which is
  the VPN/Tailscale/vEthernet adapter on many machines.
- **Fix:** Advertise `_kairos._tcp` on the desktop (`zeroconf`), add `NSBonjourServices` on iOS and resolve by `library_id`.
  Put several candidate addresses in the QR (all private IPv4s, not one). Client order: last good host -> Bonjour -> candidates.
  Watch `NWPathMonitor` to retry immediately on network change.

### H8. WebSocket zombie slots: dead peers are not detected, and the 5th connection is refused outright
- **Location:** `sync_server._websocket` (l.1420-1459), `_dispatch` (750-757); `SyncClient.changeFeed` (l.305-336).
- **Issue:** The server sends a ping every 20 s but has no pong deadline; a phone that left Wi-Fi never resets the TCP
  connection, so a dead peer is noticed only when TCP retransmission gives up (not measured; plausibly tens of seconds to minutes
  on Windows) while the slot (of `MAX_SOCKETS = 4`) stays taken. A reconnecting phone gets an immediate 503 in that window.
  The client has no ping either, so it shows "Live" on a half-open socket (a sleeping desktop is the common case). Severity is
  from reading the code; this one was not reproduced.
- **Fix:** Server: require a pong within 2x keepalive, set `SO_KEEPALIVE`/idle timers, and on a new socket from the same
  device evict the old one. Client: `task.sendPing` every ~15 s with a 10 s timeout, treat failure as end-of-feed.

### H9. Offline retry storm drains battery and keeps thumbnails queued for minutes
- **Location:** `ios/.../Components/FetchQueue.swift` `FetchRetry.run` (l.56-85).
- **Issue:** Each visible cell holds a gate slot through six backoff attempts (roughly 25 s) on `URLError`. With the desktop off,
  100 visible cells need minutes to give up, and the gate is saturated the whole time.
- **Fix:** Circuit breaker keyed on `SyncEngine.Status`: when `.offline`, fail fast with no retries and no slot hold;
  resume (one `revision` bump) when `.live`. Retry only on the first attempt for transient `URLError`s.

### H10. HTTP keep-alive desync after an early error on `/v1/import` (reproduced)
- **Location:** `sync_server._import` (l.1246-1263), `body_json` (771-778), `_error` (799-803).
- **Issue:** 415, 400 (bad sha), 411 and bad-JSON are raised before the body is read, and only 413/507 set `close_connection`.
  Reproduced: after `POST /v1/import?name=notes.txt` returned 415, the next request on the same connection was answered
  `501 Unsupported method ('AAAA...GET')`, i.e. the unread body was parsed as a request line.
- **Fix:** In `_error`, if the request has a body that was not consumed, set `h.close_connection = True` (or drain up to a cap).
  One central rule instead of per-branch.

### H11. Two concurrent uploads of the same bytes create two files (reproduced) — FIXED in Fix Block A
- **Location:** `sync_server._import` (l.1286-1309).
- **Issue:** `_imported(digest)` is checked before `_import_lock` is taken and not re-checked inside it. Reproduced: two parallel
  POSTs of the same data both answered `imported` and the inbox held `IMG_1.heic` and `IMG_1 (2).heic`. A phone that times out
  and retries while the first handler is still running hits exactly this.
- **Fix:** Re-check inside the lock, or take a per-sha256 lock before streaming.

### H12. Live Photo pairing is O(photos x videos) (measured: 20.3 s for 30k x 3k)
- **Location:** `scanner._pair_live_photos` (l.757-778).
- **Issue:** The join compares `substr/instr/rtrim` expressions, which SQLite cannot index, so it is a nested loop on every scan.
  It also ignores `content_identifier`, the actual Apple pairing key, so an unrelated `IMG_0001.MOV` next to `IMG_0001.JPG` is paired.
- **Fix:** Load `(id, dir, stem_lower, content_identifier, media_type)` once and pair in Python with a dict keyed on
  `content_identifier` (preferred) or `(dir, stem)`; O(n). Or store `stem`/`dir` columns with an index.

### H13. exiftool loses or corrupts metadata for non-ASCII file names (reproduced) — FIXED in Fix Block A
- **Location:** `scanner._run_exiftool` (l.608-630) and `_extract_batch_metadata` (632-658).
- **Issue:** Paths are passed as command-line arguments, which exiftool.exe decodes in the ANSI code page. Reproduced with three files:
  the Japanese-named file was dropped from the output, and the Czech-named one came back as `SourceFile: "???_cz.jpg"`, which does
  not match, so it falls to the single-file retry that is capped at 5 per batch of 50. The rest are stored without EXIF: no capture date
  (falls back to mtime) and no GPS, silently. `privacy_export.py:313` already uses the correct form.
- **Fix:** Write the paths to a UTF-8 args file and call `exiftool -charset filename=utf8 -@ args.txt` (verified: 3 of 3 returned).
  Drop the 5-per-batch cap or make it count-based with a user-visible summary.

### H14. Face re-grouping and the duplicate review run on the GUI thread
- **Location:** `main.py` `_recluster_faces` (l.7676-7693), `_open_duplicate_review` (7739-7760).
- **Issue:** `strict_recluster_faces(...)`, `refresh_phashes(...)` and `get_duplicate_pairs(conn)` execute on the GUI thread, papered over
  with `QCoreApplication.processEvents()`. The window freezes for the duration, and `processEvents` re-enters the event loop so the user
  can start a second recluster, an import, or close the window mid-job. The rest of the app already uses `bg_jobs`/`BackgroundAIDaemon`.
- **Fix:** Run both in `bg_jobs` with a cancellable progress toast, disable the entry points while running, and deliver results by signal.

### H15. No database integrity check, no verified backups, no restore path, and a half-initialised window on DB failure
- **Location:** `database.backup_database` (l.88-127); `main._housekeeping` (3135-3151); `main._init_db_and_load` (5081-5086).
- **Issue:** Daily backups are made with the SQLite backup API but never verified (`PRAGMA quick_check`), rotate to the newest 7 in the
  same folder as the live DB, and nothing in the code can restore them (grep: only `backup_database` is referenced). A corrupt database
  produces corrupt backups that push the last good one out of the rotation within a week. On `init_db` failure the app shows a
  modal with the raw exception and returns, leaving a main window with no library.
- **Fix:** `quick_check` the backup before promoting it, keep "last verified good" separate from the rotation, run `quick_check` at startup,
  and add a recovery dialog (restore newest verified backup / open the folder / start empty) on failure. Offer a second backup location.

### H16. ffmpeg runs with no timeout in six places; one bad video hangs the scanner and the Stop button — FIXED in Fix Block A (plus stall watchdogs on the streaming transcodes)
- **Location:** `scanner.py:153` (`make_thumbnail`), `face_engine.py:178`, `video_proxy.py:80`, `scrub_strip.py:79`,
  `ambient_music.py:378`, `privacy_export.py:606`.
- **Issue:** `subprocess.run` with no `timeout`. `render_thumbnail_bytes` (l.199) does have one (60 s), so the pattern is known.
- **Fix:** One helper `run_tool(cmd, timeout, should_stop)` that polls and kills on stop; use it everywhere.

### H17. iOS: a database that fails to open produces a dead app with no message
- **Location:** `AppModel.swift` `storeError` (l.17, 49-52), `connect` guard (l.90), `RootTabView` sheet condition (l.45).
- **Issue:** `storeError` is set but never displayed (grep). The pairing sheet requires `store != nil`, and `connect` returns silently,
  so the user sees an empty Library saying "syncing..." forever.
- **Fix:** A blocking error screen with the reason, "Retry", and "Reset local library" (the replica can be rebuilt from the desktop).

### H18. iOS: the camera-roll backup can stage up to 100 originals with no space or reachability check
- **Location:** `PhoneBackup.run` step 2 (l.72-105); `ImportQueue.enqueue`; `SyncClient.importPresent` (l.272-276).
- **Issue:** Up to 100 originals (videos are GBs; iCloud-only assets may be downloaded) are exported to `tmp`, then moved to the Outbox,
  before any byte is sent. The time budget is checked only between assets. The desktop now returns `free_bytes`/`reserve_bytes`
  (uncommitted `sync_server.py`), but the Swift side never reads them (grep) and never checks the phone's own free space.
- **Fix:** Before each asset: check phone free space (`volumeAvailableCapacityForImportantUsage`), the desktop's `free_bytes - reserve`, and
  cap staged bytes (e.g. 2 GB). Export one asset, send it, delete it, then the next ("stream, don't stage").

## 3. [IMPROVEMENTS & ENHANCEMENTS]

1. **iOS has no localisation.** The desktop ships 7 languages (Fluent); every iOS string is a hard-coded English literal and there is no
   `.xcstrings` file. Share the key set (export Fluent to `Localizable.xcstrings`) so cs/de/es/fr/ja/zh-CN work on the phone.
